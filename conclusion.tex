\section{Заключение}

Для минимизации целевой функции в ходе исследования были реализованы в ядре PostgreSQL:
\begin{itemize}
    \item Жадные подходы: $\mathrm{GOO_{cost}}$, $\mathrm{GOO_{card}}$, $\mathrm{GOO_{comb}}$.
    \item Итеративная декомпозиция на топологии:
    \begin{enumerate}
        \item Алгоритмы для обработки графового представления запроса.
        \item Варианты DP для разных топологий.
    \end{enumerate}
    \item Модификация алгоритма с открытым исходным кодом DPhypMod.
    \item Якорный подход.
    \item Расширение для планировщика PostgreSQL, которое с помощью высокоселективного доступа подставляет
    истинные значения на этапе оценки кардинальностей подпланов.
\end{itemize}

Экспериментальная оценка на двух бенчмарках
позволяют сформулировать следующие результаты.

\subsection{Выводы}

\textbf{1. Замена алгоритма перебора подпланов, при сохранении функции построения и сравнения путей, 
не является достаточным средством минимизации $t_{\mathrm{total}}$.}
DPhyp и его модификация DPhypMod рассматривают то же множество пар, что DPsize,
и на JOB дают нейтральный или отрицательный результат. 
Это связано с тем, что нарушается инвариант, при котором лесторонние планы обрабатывается первыми.
Обработка в первую очередь ветвистых планов может ухудшить $t_{\mathrm{exec}}$, для ветвистых планов
ошибки в оценках стоимости больше, чем в левосторонних.
\par
Помимо этого, большая часть времени $t_{\mathrm{plan}}$ приходится
на процедуру построения путей, число вызовов которой это $\#\mathrm{csg}$.
Для сокращения $t_{\mathrm{plan}}$ необходимо уменьшать
само пространство поиска.
\par

\textbf{2. Качество оценок кардинальностей оказывает сильное влияние на любые планирования.}
На JOB, где ошибки оценок умеренны, полный перебор DPsize
даёт хорошие планы, и якорное связывание улучшает его.
На JOB-Complex, где ошибки достигают $10^5$--$10^8$,
DPsize выбирает планы в 11 раз медленнее оптимальных \cite{JOBComplex},
и $\mathrm{GOO_{card}}$~--- жадный алгоритм без стоимостной модели~---
оказывается в 9 раз лучше DPsize.
Стоимостная модель PostgreSQL, построенная на предположении
независимости атрибутов, при нарушении этого предположения направляет
перебор в область плохих планов.
\par

\subsection{Направления дальнейшей работы}

\textbf{1. Динамический подбор параметров для якорного подхода.}
Подбор параметров во время планирования позволил бы сделать данный 
подход более гибким к разным классам запросов, схемам баз данных.
\par

\textbf{2. Обнаружение ненадёжных оценок.}
Разработка лёгковесной эвристики, маркирующей соединения
с потенциально ненадёжными оценками
(строковые столбцы, отсутствие первичного или внешнего ключа в соединении),
позволила бы использовать кардинальностную метрику, а для 
надёжных~--- стоимостную,
приближая реализацию к алгоритму $\mathcal{A}^*$,
адаптивному не только по сложности графа,
но и по качеству доступных статистик.
\par

3. Использование стоимостных критериев и селективности для определения якорей и их участков 
на единичных отношениях.
\par


4. Выработка других критериев и апробация для применения якорного подхода:
\begin{itemize}
    \item Доля потенциальных якорных вершин. 
    \[
    \rho_a(G) = \frac{|\{\,v \in V : \text{A\_condition}(v) \text{ выполнено}\,\}|}{|V|},
    \] 
    где $\text{A\_condition}(v)$~--- якорное условие.

    \item Доля покрытия графа якорными участками. 
    \[
    \rho_z(G) = \frac{|\bigcup Z_i|}{|V|},
    \] 
    где $Z_i$ --- якорный участок.

    \item Доля небезопасных или селективных рёбер. 
    \[
    \rho_e(G) = \frac{|\{\,e \in E : \text{sel}(e) \leq \text{threshold\_selectivity} \lor \text{E\_unsafe}(e) \text{ выполнено}\,\}|}{|E|},
    \]
    где $\text{E\_unsafe}(e)$~--- условие небезопасности.

    \item Стоимостные критерии для якорного условия.
\end{itemize}
